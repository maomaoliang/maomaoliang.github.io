# MCP已死，CLI当立

> 作者：IT屠狗辈（公众号：AI扫盲人）｜2026-03-16

## 核心观点

MCP（Model Context Protocol）从设计之初是为"妥协"而生的产物，无法承受 AI Agent 时代的真实考验。以 CLI 为主要驱动的 Agent 框架（如 OpenClaw）才是更务实的方案。

## MCP 的困境

- **覆盖不足**：99% 的软件没有 MCP Server，MCP 假设了一个"软件已经准备好被 AI 调用"的世界，但这个世界不存在
- **中心化思维**：需要有人为每个工具专门编写 Server，维护成本高
- **长尾问题**：企业内部工具永远不可能有 MCP Server，除非专门开发

<!-- more -->

## CLI 的六大优势

1. **零门槛发现**：不需要预先配置，只需系统 PATH
2. **天然可组合**：管道机制天然支持工具串联
3. **无状态更可靠**：没有连接管理的复杂性
4. **LLM 的"母语"**：CLI 命令结构与自然语言高度相似，LLM 训练数据中包含海量 CLI 知识
5. **真实软件**：调用真实软件而非 API 模拟品
6. **经济高效**：管理数百个工具时成本优势明显

## OpenClaw 的验证

- 2025年11月发布，3 个月内 GitHub Star 从 9K 飙至 214K
- 生态中 **60%+ 工具通过 CLI 完成**，40% 使用 MCP（主要是 GitHub、Google Drive 等主流平台）
- 衍生生态不约而同选择 CLI 优先架构

## 未来预判

- **短期（1-2年）**：CLI 成为 Agent 的"操作系统 API"，CLI 工具市场兴起
- **中期（3-5年）**：CLI 成为 Agent 交互的"普通话"，Agent 互联网雏形出现
- **长期（5-10年）**：接口范式的终极统一

## 个人思考

这篇文章的观点有一定道理但也有偏激之处。MCP 和 CLI 并非完全对立——实际项目中（如我自己的知识库），MCP 适合有明确 API 的场景（如飞书同步），而日常文件操作确实 AI 直接用 CLI/文件系统更高效。关键不是"哪个死了"，而是在合适的场景用合适的工具。
